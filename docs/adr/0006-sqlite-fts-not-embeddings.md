# ADR 0006: ベクトル検索を使わず SQLite FTS5 で引く

- 状態: 採用
- 日付: 2026-08-13

## 背景

「会議の RAG として使いたい」という要件がある。
RAG と言われると埋め込み + ベクトル DB が既定の選択肢に見える。

## 決定

**SQLite FTS5 (trigram トークナイザ) のみ**を使う。埋め込みは入れない。

短いクエリ(3文字未満)や特殊文字を含むクエリは `LIKE` にフォールバックする。
trigram が使えない古い SQLite では unicode61 + `LIKE` に落ちる。

## 理由

1. **規模が合わない** — 同時 active な案件は 10 件程度、メインは 5 件。
   この規模では埋め込みの再現率の利点が出る前に、案件フィルタと日付フィルタで
   候補が十分に絞れる
2. **実行環境** — 常時稼働させる先は低スペックな小型機(ARM シングルボード等)を
   想定している。そこで埋め込みモデルを動かす手間と、得られる利点が見合わない
3. **文脈の与え方が違う** — このツールの主戦場は
   「類似文書を探す」ではなく「**この案件について構造化済みの事実を全部渡す**」。
   それを担うのは検索ではなく `comdiary context` (context pack) で、
   これは決定論的な SQL の組み立てで作れる
4. **説明可能性** — なぜこの結果が出たかが読める。壊れたときに直せる

trigram を選んだのは日本語のため。unicode61 は日本語の語境界を切れず、
「切替日」のような部分文字列検索が効かない。

## 帰結

- 索引はすべて derived。`.comdiary/state.sqlite` は消しても `comdiary reindex` で復元できる
- 案件数が数十を超える、または「言い回しが違う過去の議論を探したい」が
  実際に困りごとになったら、この ADR を見直す
- 依存が pure Python だけで済むので、arm64 の小型機でも Windows でも `uv sync` で動く
