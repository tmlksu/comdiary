# 既知の制約と、環境ごとに決めること

設計上まだ決め切っていないこと、環境によって調整が要ること、
そして「そういう仕様です」と分かっていないと困る挙動をまとめてあります。

各項目に **現状** (いま何をしているか) を書いてあるので、
自分の環境で違う判断が要るときはそこを起点にしてください。

---

## 議事録の書式に依存する

comdiary は文字起こしの**話者ラベルを読めること**を前提に、いくつかの判断をしています。
特に共通マイクの判定 (→ [ADR 0004](adr/0004-shared-mic-invalidates-speaker-attribution.md))
はラベルが読めなければ機能しません。

対応している書式:

```
田中 太郎: こんにちは
**田中 太郎**: こんにちは
00:03:12 田中 太郎: こんにちは
[00:03] 田中: こんにちは
```

**現状:** 上記に当てはまらない書式は「ラベル無し」として扱い、
`mic_mode: unknown` にして話者帰属を一切行いません。
壊れるのではなく、安全側に倒れます。

自分の書式が読めているかは、取り込み後に会議正本の「収録状況」を見れば分かります。
発言比率が出ていなければパーサが取りこぼしています。
その場合は `src/comdiary/transcript.py` の `_PATTERNS` にパターンを足してください。

## 取り込みホスト — Google Drive ストリームは Windows / macOS にしかない

Google Drive for Desktop のストリーム マウント (`G:\` など) は Windows と macOS
にしか生えません。**常時稼働の Linux 機から直接は読めません。**

| 案 | 長所 | 短所 |
|---|---|---|
| A. Windows で定期実行 (タスク スケジューラ) | Drive を直接読める。追加構成ゼロ | PC が起動している時だけ動く |
| B. Linux + rclone で Drive をマウント | 常時稼働できる | rclone の認証・マウント運用が増える |
| C. Windows で取り込み → 台帳を別ホストに同期 | いいとこ取り | 同期経路が増え、競合の余地が出る |

**現状:** どれでも動くように、コードは OS 非依存にしてあります
(`fcntl` を使わない可搬ロック、パスは `pathlib` のみ、
別ボリュームへの移動は `shutil.move` にフォールバック)。
設定手順は [operations.md](operations.md) に Windows / Linux の両方があります。

## `quiet_seconds` — 取り込む前にファイルが落ち着くのを待つ時間

**現状:** 最終更新から `quiet_seconds` (既定 60秒) 静止したファイルだけを対象にします。

適切な値は**書き出し側の性質**で決まります。

| 書き出し側 | 目安 | 理由 |
|---|---|---|
| 完成した文書を1回で書き出す | 60 程度 | 同期(Drive ストリーム等)が届けば十分 |
| 少しずつ追記していく | 書き込み間隔より長く | 途中で掴むと議事録が切れる |

追記型で短すぎると、**途中まで取り込まれた議事録が正常なものとして残ります。**
要約が短いだけに見えるので、後から気づけません。迷ったら長めに倒してください。
1時間おきの実行なら 900 でも取りこぼしは出ません。

`comdiary ingest status` で待機中の件数が見えます。

## 会議日時の決め方 — 日付と時刻は別々に取る

**ファイル名が `yyyy-mm-dd` だけ、というのはよくあります。**
その場合に日付ごと信用すると、同じ日の会議が全部 00:00 になり、
昼会と夕会の順序が消えます。そこで日付と時刻を別の出所から取ります。

| 順 | 出所 | 見る場所 |
|---|---|---|
| 1 | `filename` | ファイル名 (`2026-08-13-...`, `2026-08-13-1200-...` 等) |
| 2 | `body` | 本文の先頭 2000 文字 (`日時: 2026年8月13日 14:30`、`開始時刻: 16:05` 等) |
| 3 | `llm` | LLM が読み取った日時 |
| 4 | `mtime` | **ファイルの更新時刻** (最後の手段) |

日付が決まっても時刻が無い場合、**同じ日付の**時刻を後続の出所から借ります。
日付が違うものは借りません — 本文には締切や次回日程など、この会議の開始時刻では
ない日時がいくらでも出てくるためです。

時刻だけの記載は `日時` `時刻` `開始` `Time` などのラベルが付いている場合のみ拾います。
裸の `HH:MM` を拾うと、発言ごとのタイムスタンプ (`00:03:12 田中: ...`) を
会議の開始時刻と誤認するためです。

結果は `date_source` / `time_source` として会議正本の frontmatter と
`comdiary ingest run` の出力に残ります。

```
ok   2026-08-13-昼会.md → 昼会 (2026-08-13 12:00)
     マイク: unknown / 話者帰属: uncertain / 日付: filename / 時刻: body / LLM呼び出し: 3
```

- **時刻が見つからない場合**、`time_source` は `unknown` になり、
  会議正本には `2026-08-13 (時刻不明)` と出ます。**00:00 とは書きません。**
- **`mtime` に落ちた場合は警告が出ます。** 文字起こしが会議より後に書き出される経路
  (通知が届いてから別のジョブが取得・変換する等) では、ファイルの更新時刻は
  会議の時刻ではなく、数時間〜数日ずれることがあるためです。

`date_source: mtime` や `time_source: unknown` が並ぶようなら、
ファイル名か本文冒頭に日時があるのに読めていない可能性があります。
パターンは `src/comdiary/ingest/pipeline.py` の
`_DATE_PATTERNS` / `_LABELLED_TIME` に追加できます。

## `topics` は「同じ言葉で呼ばれたもの」しか繋がない

`comdiary topics` は論点を会議・案件をまたいで集計しますが、
**集計キーは LLM が付けたラベルの文字列一致**です。

つまり、同じ根っこの問題でも**現れ方が違えば別の論点として並びます。**
たとえば「移行手順書が特定の人の頭の中にある」「デザインの意図が本人にしか
分からない」「担当が休むとレビューが止まる」は、人が見れば同じ属人化の話ですが、
LLM は目の前の現れ方をラベルにするため `移行手順書` `デザイン意図` `レビュー体制`
と分かれます。

**現状:** 既出の論点を抽出プロンプトに戻して表記のゆれ(`納期` / `スケジュール` /
`期日`)は抑えていますが、**別の言葉で呼ばれる同じ問題を統合することはしません。**

これは意図的です。「これらは同じ問題だ」という判断は解釈であって抽出ではなく、
機械が勝手に束ねると根拠のない繋がりが台帳に残ります。
`topics` の一覧は**その判断をするための材料**として使ってください。
一覧を眺めて「この3つは同じ話だ」と気づくのが、点が線になる瞬間です。

## 温度感(signals)の語彙は固定

`escalation / resistance / enthusiasm / hesitation / silence / repetition /
deflection / concern` の 8 種類です。自由記述にすると後から人・論点ごとに
集計できなくなるため、意図的に固定しています (→ [schema.md](schema.md))。

**現状:** 「淡々と進んだ議題では空でよい」とプロンプトで指示しているので、
記録量は少なめに出ます。

**語彙を増やす場合は過去データの再抽出が必要になります**
(`meetings/*.json` は残っているので原文からやり直せますが、LLM 呼び出しが再度かかります)。
運用の早い段階で決めたほうが安く済みます。プロンプトは
`src/comdiary/llm/prompts.py` の `SIGNAL_GUIDE`。

## 逐語引用は会議メモにそのまま載る

温度感の `quote` (逐語引用) と `evidence` は、案件配下の会議メモに載ります。
資料作成時には効きますが、内容によっては扱いに注意が要ります。

**現状:** 分離していません。原文全体は `sources/raw/` にアーカイブされ、
`meetings/` には抽出結果と引用が載ります。

引用を落としたい場合は `src/comdiary/templates/_segment_body.md.j2` の
`{% if sig.quote %}` ブロックを外し、`comdiary rerender` を流せば
既存の台帳からも消えます (正本 JSON には残ります)。

## チャット・メールの取り込みは手動

**現状:** `comdiary ingest add` でファイル・フォルダ・標準入力から入れます。
`ingest run` のような自動巡回は議事録フォルダに対してだけ動きます。

```bash
comdiary ingest add ./export.txt --kind chat -p <project-id>
cat mail.eml | comdiary ingest add - --kind mail -p <project-id>
```

定常的に流し込みたい経路があるなら、そのフォルダを別の設定ファイル
(`conf.d/` や `--config`) で `inbox` に指定して `ingest run` を回すのが早いです。

## `registry/people.yaml` は初期状態で空

`comdiary concerns --person <名前>` のように人単位で引くには、
文字起こしに出てくる話者ラベルと人物 id の対応が必要です。

**現状:** 空のまま動きます。未登録の話者はラベル文字列のまま集計されるので、
表記ゆれ (「田中」と「田中 太郎」) が別人として数えられます。

主要メンバーを登録しておくと初回から人物単位の集計が効きます。
`aliases` には文字起こしに現れる表記を全部書いてください。

## Copilot CLI は不正なモデル名でも終了コード 0 を返す

`--model` に使えないモデル名を渡すと、Copilot CLI は stderr にエラーを書いて
**stdout を空にしたまま終了コード 0 で終わります**。黙って失敗します。

**現状:** 空応答を検知して stderr を添えたエラーにしています。
事前確認には実際に1回呼ぶしかないので、そのためのコマンドがあります。

```bash
comdiary doctor --probe
```

既定は `model = "auto"` (Copilot が選ぶ) です。使えるモデル名は
アカウントと CLI のバージョンによって変わります。

## Copilot CLI の非対話モードは `--allow-all-tools` を要求する

CLI の仕様で、非対話モード (`-p` / stdin) には `--allow-all-tools` が必要です。
つまり抽出中に Copilot がシェルやファイル操作を実行できる状態になります。

実際には「テキストを読んで JSON を返す」だけのタスクなので通常は何も起きませんが、
**文字起こしの中に指示めいた文字列が含まれていた場合の挙動は保証できません。**

**現状:** `--allow-all-tools --no-color --log-level none` のみを渡しています。
絞りたい場合は設定だけで追加できます。

```toml
[llm]
extra_args = ["--deny-tool", "shell"]
```

## Gemini API は議事録を「1 + セグメント数」回ぶん課金しうる

1つの会議は分割1回 + セグメントごとの抽出で処理され、そのすべてが議事録全文を
必要とします。定額の Copilot CLI では見えなかったこの構造が、従量課金の API では
そのまま請求に出ます。6セグメントの昼会なら全文7回ぶんです。

**現状:** Gemini バックエンドは既定で議事録を1回だけアップロードし
(`cachedContents`)、以降の呼び出しはそれを参照します。文書を処理し終えた時点で
キャッシュは削除します。キャッシュは生きている間ずっと課金されるためです。

効かない場合が2つあります。どちらも取り込み自体は成功しますが、全文が毎回送られます。

- 議事録が `cache_min_chars` (既定 2000) より短い。モデルの最小キャッシュサイズに
  届かないので、作成を試みずにそのまま送ります
- キャッシュ作成そのものが失敗した。以降その実行中は作成を再試行しません
  (セグメントごとに失敗した呼び出しを課金されるのを避けるため)

## Gemini の `responseSchema` は JSON Schema そのものではない

pydantic が吐く JSON Schema は入れ子モデルを `$ref` / `$defs` で表し、
`X | None` を `anyOf: [..., {"type": "null"}]` で表します。Gemini が受け付けるのは
OpenAPI 3.0 のサブセットで、どちらも解釈できません。

**現状:** `src/comdiary/llm/schema.py` が変換します。参照を展開し、null 分岐を
`nullable` に畳み、型名を proto の列挙値 (大文字) にします。

表現しきれないスキーマ (再帰、`dict[str, X]` のようにキーを列挙できないオブジェクト) は
**黙って落とさずに変換を諦め**、プロンプトでスキーマを説明する従来の方式と
検証リトライにフォールバックします。制約を1つ黙って外すと、モデルは pydantic が
弾く形を返す自由を得てしまい、失敗がモデルのせいに見えるためです。

## Gemini は thinking で出力予算を使い切ることがある

`thinkingConfig` を指定しないと、モデルは推論に `maxOutputTokens` を消費できます。
長い議事録では、本文が1文字も返らないまま `finishReason: MAX_TOKENS` になり得ます。

**現状:** 空応答と打ち切りをそれぞれ別のエラーにし、どちらのつまみを回せばよいかを
メッセージに書いています。抽出は機械的な作業なので `thinking_budget = 0` でも
実用になります。

```toml
[llm.gemini]
max_output_tokens = 16384
thinking_budget = 0
```

## LLM は事実を少しだけ盛ることがある

構造化抽出は概ね正確ですが、決定事項をやや具体的に書きすぎることがあります
(例: 「予備日を1週間取る」→「9月1日を試行日、9月2日〜8日を予備期間とする」)。

**現状:** 各要素に `confidence` を持たせ、原文を `sources/raw/` に必ず残しています。
決定事項が重要な局面では原文を確認できるようにしてあります。
会議正本には原文アーカイブへのパスが載ります。

## Windows のパスはシングルクォートで囲む

TOML のダブルクォート文字列では `\` がエスケープ文字です。

```toml
inbox = "G:\マイドライブ\memos"   # NG: Invalid hex value (\U が Unicode エスケープ扱い)
inbox = 'G:\マイドライブ\memos'   # OK: リテラル文字列
```

**現状:** `comdiary init` が生成する設定ファイルは、すべてのパスを
シングルクォートで書き出します。手で追記するときも合わせてください。
読み込みに失敗した場合は、ファイル名と原因を添えたエラーが出ます。
